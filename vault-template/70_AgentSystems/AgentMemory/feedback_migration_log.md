# 规则：版本迁移必须在 99_Meta 留档

任何对 SelfStudyOS 框架本身的版本升级或结构性迁移（例如上游 v0.x → v0.y 升级、目录重组、入口分离、新机制注入），都必须在 `99_Meta/` 留下一份迁移记录。

**Why:** 系统搭建里程碑不要污染 `Review/progress.md`（按 v0.3 新规，那一页只记真实学习证据）。同时迁移过程的"为什么改、改了什么、怎么回滚"如果不留档，几周后就会忘干净，下次升级时无据可循。2026-06-10 那次升级就是因为没规则约束，agent 把"系统阶段 v0.1→0.3 升级中"写进了 `Review/progress.md`，需要后期清理。

**How to apply:**

- 触发条件：任何下列情况都要建迁移记录
  - 上游开源框架版本升级（哪怕是小版本）
  - 目录结构重组（新增/删除/重命名顶层目录）
  - 新机制注入（如入口分离、5 行收口、stale 规则之类的系统级特性）
  - agent 工作流硬约束的批量变更

- 文件路径：`99_Meta/migration_<YYYY-MM-DD>.md`
- 必须包含的字段：
  1. 触发原因（哪个上游版本，发布日期）
  2. 执行阶段表（阶段编号 / 内容 / 状态）
  3. 新增机制清单（不含具体改动细节，链向上游 CHANGELOG）
  4. 被保留未动的关键数据（确认没破坏现有学习证据）
  5. 已发现并修复的遗漏（每个遗漏的原因 + 修复方案）
  6. 回滚命令（具体可执行的 PowerShell / bash 命令）
  7. 后续验证计划（第一次完整闭环什么时候做）

- **不要**把系统搭建里程碑（"v0.3 升级中"、"已完成阶段 1/2/3"）写进任何 `Review/` 或 `CourseOS/*/progress.md`。那些页面只记学习证据。

- 留档时机：迁移**全部完成后**立刻写，不要拖。新对话开启时 agent 应主动检查 `99_Meta/` 最近的 migration 文件，了解上次升级的边界。

参考样例：[[99_Meta/migration_2026-06-10|migration_2026-06-10]]（v0.1 → v0.3）。
